# AI 辩论模拟平台

输入论题与正反方观点，由 **八位独立的 AI 辩手**（正反各四人）按正式赛制完成一场辩论：各自联网检索并核对证据 → 立论 → 驳论 → 质询与小结 → 自由辩论 → 总结陈词，最后由多位 AI 裁判独立打分、投票决出胜负和最佳辩手。

辩手模型可以按队伍选择 DeepSeek、智谱 GLM 或千问（默认 `deepseek-flash`），思考强度也可以按队伍调整；联网检索使用博查 Web Search API。

## 快速开始

### 方式一：双击启动（macOS）

在 Finder 中双击 `start-local.command`。它会自动完成：

- 检查 Node.js（需要 18+）
- 首次运行时安装依赖（旧淘宝镜像失效时自动改用 npmmirror）
- 创建 `.env`；未配置 DeepSeek API Key 时，可当场输入（输入不回显，保存到 `.env` 并设为仅本人可读），也可选择演示模式；博查 API Key 同样可当场输入，直接回车则跳过联网检索
- 端口被其他程序占用时自动顺延到下一个端口；平台已在运行时直接打开浏览器
- 服务就绪后自动打开浏览器

关闭终端窗口或按 Ctrl+C 即可停止服务。想固定使用演示模式，可在 `.env` 中设置 `DEBATE_MOCK=1`。

> 如果双击时 macOS 提示无法打开，可以右键选择「打开」，或在终端运行 `chmod +x start-local.command`。

### 方式二：命令行

```bash
npm install
cp .env.example .env    # 填入 DEEPSEEK_API_KEY 和 BOCHA_API_KEY；要用智谱 / 千问再填 ZHIPU_API_KEY / DASHSCOPE_API_KEY
npm start               # http://localhost:3000
```

没有 API Key 时可以先用演示模式看完整流程（不调用 API、不联网，内容为占位数据）：

```bash
npm run demo
```

> 如果 `npm install` 报 `registry.npm.taobao.org ... certificate has expired`，说明全局配置的是已停用的旧淘宝镜像，可改用 `npm install --registry=https://registry.npmmirror.com`。

## 辩论动态演示（占位内容）

启动服务后访问 `/demo.html`（主页右上角「辩论动态演示」）。页面按实录顺序回放一场八位辩手（正反各四人）的完整辩论：

- 每次发言前，辩手独立思考 5–10 秒，显示齿轮动画；随后发言逐字出现在上一段发言下方。正方在左，反方在右。
- 顶部席位栏实时显示谁在思考、谁在发言。控制区可以暂停、切换 1×/2×/4× 速度、跳过当前等待，或直接看结果。
- 辩论结束后依次展示评委点评（判决、胜负关键、辩手评分、最佳辩手、各环节点评、改进建议），最后公开辩手资料文件夹。

**辩手是辩论的主体**：每位辩手各自检索、拥有自己的资料文件夹，同队四人共享资料，对方的资料看不到。发言前辩手能看到公开发言记录和本方资料（思考卡片上会标明可见范围）。资料在赛后才公开，公开后可以点击发言卡片上的资料标记、席位或文件树查看。

占位数据直接读取项目根目录下的文件，修改后刷新页面即可生效：

| 文件 | 用途 |
|---|---|
| `辩论实录_难民管控.md` | 发言内容。按 `## 正方一辩 · 立论` 这样的标题切分；质询用 `**问X：**`、`1. 问题`、`**X：** 回答`；自由辩论用 `**X：** 发言` |
| `评委点评.md` | 判决、胜负关键、各环节点评、评分表、最佳辩手、可改进之处 |
| `辩手资料_难民管控/<正方\|反方>/<X方Y辩>/*.md` | 每位辩手自己的资料。文件头部写明 `标题`、`类型`、`来源`、`使用环节`（逗号分隔，如 `立论, 质询`），演示页据此标出每段发言用到了几份资料 |

文件路径配置在 `src/demo/placeholder.ts` 的 `DEMO_FILES`。

## 辩论流程

```
赛前准备：8 位辩手并行，各自按辩位职责联网检索 → 打开网页核对原文 → 整理证据，汇入本方共享的证据库
封存：    每条证据再打开一次原网页复核，打不开、摘录不在或出处无法确定的删除 → 证据库封存
立论：    正方一辩 → 反方一辩（约 8 分钟，6-9 分钟均可）
驳论：    正方二辩 → 反方二辩
质询：    正方三辩向反方一辩、二辩各提 2 问并小结；反方三辩同样质询正方并小结
自由辩论：双方交替，每人一次
总结陈词：反方四辩 → 正方四辩
评委评议：N 位裁判独立评分 → 代码计票 → 主裁判综述；各辩手个人得分取平均，最高者为最佳辩手
```

发言依次进行，后发言的辩手能听到之前所有公开发言。直播页（`live.html`）实时显示谁在检索、构思或撰写，逐段呈现发言；比赛结束后公开每位辩手的证据库、检索记录、丢弃的网页和构思笔记。

## 八位辩手是八个独立的 Agent

每位辩手（`src/agents/debater.ts`）都有自己的：

- **身份与职责**：所在方、辩位和该辩位的任务（一辩立论、二辩驳论、三辩质询、四辩总结）；
- **人设**（`src/agents/personas.ts`）：各自的论证习惯、语言风格、招牌打法和检索偏好，如正方一辩「架构师」、反方三辩「律师」。人设只影响切入角度和表达，不改变立场、职责和引用规则；双方偏分析和偏表达的风格按辩位交叉搭配，改风格直接改这个文件；
- **检索分工**：按辩位职责自己决定搜什么、自己核对和整理，证据记在自己名下（P2-3 = 正方二辩检索到的第 3 条）；
- **私有记忆**：每次重要发言前的构思（逻辑链、每条证据证明哪一步），只有自己能回看；
- **可见范围**：公开发言记录、本方证据库、对方已公开的证据和证据核查结果，与真实比赛中的辩手一致。

**队友之间共享证据，双方之间不共享。** 同队四位辩手的证据汇成本方证据库，任何一位都可以引用队友检索到的证据（包括还没公开的）；构思仍然只有本人可见。同队并行检索时，同一个网页只由最先搜到的人打开核对、整理，同一个数据在本方证据库里只留一条。对方的证据只有在发言中被引用时才会公开；公开之后可以回指、反驳或质疑，但不能当作本方的证据。引用对方尚未公开的证据会被判为违规（你方不可能看到）。裁判只看公开信息。

## 证据可核对：每条证据都打开网页核对过原文

旧版只核对「摘录是否出现在博查返回的摘要里」，从没打开过网页，结果很多链接打不开或内容对不上。现在每条证据入库前，代码都会逐一核对（`src/agents/researcher.ts`、`src/search/page.ts`）：

1. **网页能打开**：实际请求网页，要求返回正常、有正文。平台运行在你本机，这里能打开的网页，你在同一网络下也能打开。
2. **搜索摘要与网页对得上**：摘要里的句子要能在网页正文中找到；对不上的（常见于靠脚本渲染的页面）直接丢弃。
3. **摘录逐字出现在网页正文里**：模型从网页正文节选中摘录原文，代码在网页全文中逐字核对（忽略空白、标点和全半角差异）。
4. **出处名称真实**：出处（如「麦肯锡全球研究所」）必须原样出现在网页中，否则改用网站名；连网站名都没有、出处无法确定的证据直接删除。
5. **同一数据只留一条**：同一个统计数字被多个网页转载，只保留一条。

证据要用能直接打开的原始出处，以下三类站点默认屏蔽（完整名单见 `src/config.ts` 的 `DEFAULT_BLOCKED_DOMAINS`，可用 `BLOCKED_DOMAINS` 追加）：

- **转载、自媒体与社区平台**：今日头条、搜狐、网易、腾讯（含公众号）、新浪、凤凰、百家号、知乎、CSDN、豆瓣、360doc 等。门户的时政内容多转自原媒体，研究员会被要求去找最初发布的机构或媒体。
- **文库与报告聚合站**：豆丁、道客巴巴、原创力、人人文档、百度文库、报告盒子、外唐等，全文要登录、付费或下载。
- **学术数据库**：知网、万方、ResearchGate，要登录才能看原文。

屏蔽名单作为博查的 `exclude` 参数传入，这些站点在搜索时就被排除；漏网的结果不会交给模型，直接记为丢弃。被丢弃的网页及原因在赛后「丢弃的网页」中可查，每条证据都记录了核对时间。

## 证据规则：只在赛前收集，数量有上限

- **只在赛前准备中收集**：八位辩手只能在赛前准备中检索。检索结束后，系统把每条证据的原网页再打开一次复核：网页打不开、摘录已不在正文里、出处无法确定的证据直接删除（记入「丢弃的网页」，标着「封存前复核」），然后按顺序重新编号并封存证据库。立论开始后，任何辩手都不能再收集新证据，检索代码在封存后会直接拒绝执行。证据核查员为核查质疑而做的联网搜索不进任何一方的证据库。
- **收集上限**：每方证据库最多 20 条（`EVIDENCE_PER_SIDE`，可设到 30，超过 30 按 30 算），按辩位平均分给四位辩手（20 条即每人最多 5 条）。去重和复核之后，实际入库的往往少于上限。
- **使用上限**：每方全场最多使用 9 条证据（`MAX_EVIDENCE_USED_PER_SIDE`）。一条本方证据第一次在发言中被引用就算用掉一条，不论是哪位辩手引用；之后回指不再计数，引用或反驳对方的证据不计入。辩手每次发言前都能看到本方已用几条、还剩几条；构思里计划首次使用的证据超出剩余额度，要求重新构思；发言超出，要求修改；修改后仍超出的引用按出现顺序剔除（证据不公开），记为违规交裁判组扣分。直播页的席位栏实时显示双方的证据使用数。

## 先有推理，后有证据

旧版的问题是：论点几乎全是引用拼接，同一个数据在立论、驳论、总结里被反复完整讲述。现在：

- **先构思、后撰写**：立论、驳论、质询小结、总结陈词之前，辩手先私下写出构思——每个论点 3-5 步推理链，并标明每条证据证明的是哪一步。代码检查推理链步数、每点证据数、证据是否在本方证据库中、是否超出本方剩余的证据额度、不同论点有没有用同一个数据，不合格就重新构思。构思与撰写都用本方选定的思考强度。
- **限制引用密度**：每个论点最多引用 2 条证据；一段发言里含引用的句子不超过 45%（`MAX_CITATION_RATIO`），超出就要求删减引用、补充推理。
- **不重复**：同一条证据、同一个数据在一段发言里只讲一次；已经公开过的证据再提时只需简短回指，不再重复出处和内容。
- **引用写法**：首次引用先说出处、再讲内容，编号只作为句末的〔P1-3〕标注（P1-3 = 正方一辩的第 3 条证据），页面上显示为上标脚注和「引用来源」列表。
- **立论约 8 分钟**：按每分钟 240 字估算，立论以约 1920 字为宜，6–9 分钟（1440–2160 字）都算合格，只有超出这个范围才要求修改。撰写时给出开场、各论点、结语的字数预算；超长或过短时指出偏离预算最多的部分。
- **其他发言的篇幅**：驳论 600–800 字、质询小结 400–550 字、总结陈词 700–950 字，明显超出或不足时要求修改；质询、答问、自由辩论只检查是否超长。

不符合要求时，辩手拿到上一稿和具体修改意见重写（重要发言最多两次）。修改后仍不合格的写入运行日志；引用违规（不存在、看不到或已判不成立的证据，没出现过的论点）剔除后交给裁判扣分。

## 证据质疑

每方全场最多质疑对方证据 3 次（`MAX_CHALLENGES_PER_SIDE`）。辩手在驳论、小结、自由辩论、总结陈词中，如果有具体理由怀疑对方某条已公开的证据，可以提出质疑。中立的证据核查员（`src/agents/factcheck.ts`）当场：

1. 重新打开证据的原网页，看能否打开、摘录是否还在；
2. 用博查联网搜索这条证据讲的事实，看有没有其他来源佐证；
3. 对照原文判断证据本身和发言中的转述是否忠实。

结论分为「成立 / 部分成立 / 不成立」，作为一段公开的「证据核查」插入发言记录。判定不成立的证据此后不得再引用，裁判不予采信；无理的质疑同样会被裁判看在眼里。

## 双方模型与思考强度

发起辩论时，在表单里为正反双方各选一个模型和思考强度。**只能按队伍选**：同队四位辩手（检索、整理证据、构思、发言）用同一个模型，不能给单个辩手换模型。这样可以让不同模型直接对辩，也可以同一模型换不同思考强度对比。

| 模型 | 编号 | 思考强度（由低到高） | 需要的密钥 |
|---|---|---|---|
| DeepSeek V4.1 Flash | `deepseek-flash` | low / high（默认）/ max | `DEEPSEEK_API_KEY` |
| DeepSeek V4 Pro | `deepseek-v4-pro` | low / high（默认）/ max | `DEEPSEEK_API_KEY` |
| 智谱 GLM-5.3（旗舰） | `glm-5.3` | low / high / max（默认） | `ZHIPU_API_KEY` |
| 千问 Qwen3.8-Max（旗舰） | `qwen3.8-max` | low / medium / xhigh（默认） | `DASHSCOPE_API_KEY` |

- 档位用各家 API 的原生取值（DeepSeek、智谱的 `reasoning_effort`；千问开启 `enable_thinking` 后的 `reasoning_effort`），「默认」是各家 API 自己的默认档位。思考强度用于构思、发言和整理证据；检索时决定搜什么只用该模型的最低档。
- 没有配置密钥的厂商在下拉框里不可选；页面会记住上次的选择。
- 选择随辩论记录保存，续跑时沿用；直播页顶部显示双方用的模型。旧记录没有保存模型，续跑时按 `.env` 的默认配置。
- 裁判组与证据核查员不随队伍变化，固定使用 `JUDGE_MODEL`（同样可以是上表任一模型）。双方都用非 DeepSeek 模型时，记得把裁判也配置成有密钥的模型。
- 最高档被 `max_tokens` 截断时自动降一档重试，不会让整场辩论中止。

## 模型在这个平台里做什么

| 环节 | 模型的工作 | 代码做什么 |
|---|---|---|
| 检索 | 决定搜什么（函数调用） | 调用博查、打开网页、核对原文、去重、丢弃不可核对的网页 |
| 整理证据 | 从网页正文中摘录原文、写出证据陈述和出处 | 逐字核对摘录、核对出处 |
| 构思 | 设计推理链、为每一步分配证据 | 检查推理链步数、证据归属和重复 |
| 发言 | 按构思撰写 | 检查引用、密度、重复、时长，不合格要求重写 |
| 质疑核查 | 对照原文判断是否忠实 | 打开原网页、联网搜索 |
| 评议 | 裁判打分、主裁判综述 | 计票、平均分、最佳辩手 |

证据的真实性完全由代码保证，模型只负责「找」和「写」；逻辑质量由「先构思」的流程和代码检查共同约束。想进一步增强逻辑，把队伍的思考强度调高，或换用 `deepseek-v4-pro` 等更强的模型；预算允许时再把 `JUDGE_MODEL` 也换成更强的模型。

## 费用：前缀缓存与用量统计

一场辩论要调用模型上百次（8 位辩手检索整理、约 32 段发言的构思与撰写和修改稿、质疑核查、裁判评议），而每段发言都要带上此前的全部发言记录和证据库，越往后单次输入越长，输入 token 是主要开销。平台为此做了两件事：

- **让长前缀命中缓存**：DeepSeek、智谱和千问都会缓存请求的前缀，前缀与之前的请求相同的部分按缓存价计费（缓存按模型区分，同队四人用同一个模型正好共享）。给辩手的材料按「全场相同 → 本方相同 → 本人」排列：系统提示对八位辩手完全相同（身份、剩余质疑次数等放到后面），接着是公开发言记录、本方证据库、对方已公开的证据，最后才是本人的身份、构思、任务和 JSON 格式要求。这样每次调用只有新增的发言和本人的部分按原价计费。给辩手的证据卡片也做了精简（不带网页标题和链接，原文摘录截到 200 字）。
- **用量统计**：每次调用都累计模型返回的 usage，按环节（检索、构思、发言、核查、评议）和模型分类。比赛结束（或出错中止）时写一行「模型用量」到运行日志和终端，包括调用次数、输入 token、缓存命中率、输出 token 和其中的思考部分，可以和各家控制台的账单对照；明细保存在辩论记录的 `usage` 字段。

检索时决定搜什么的函数调用用该模型的最低思考强度；函数调用次数用完就结束，不再多请求一次让模型收尾。想再省，可以调低队伍的思考强度、减少 `FREE_DEBATE_TURNS` 或 `CROSS_QUESTIONS_PER_TARGET`。

DeepSeek 与智谱的思维链计入 `max_tokens`，平台按各家的上限设置（DeepSeek `high` 64K、`max` 128K，智谱 128K）；千问的 `max_tokens` 只限制回复，不传。仍被截断时自动降一档思考强度重试。

## 断点续跑

辩论因模型报错、网络问题或服务重启而中断时，打开这场辩论的页面，点「从断点继续」（接口 `POST /api/debates/:id/resume`）：

- 已完成的发言、证据库、构思、质疑和违规记录原样保留，从第一段缺失的发言接着跑，只有剩下的部分调用模型；
- 已经完成的构思、已经交卷的裁判直接沿用；提出后还没核查完的质疑补跑核查；赛前准备中断的，只补没准备完的辩手；
- 证据库封存后绝不会再封存一次（封存会给证据重新编号）；
- 质询轮数、自由辩论次数在开赛时存进记录（`rules`），续跑沿用，不受之后修改 `.env` 的影响；快进时逐段核对发言人与类型，对不上就报错，不硬接；
- 同一场辩论只能由一个服务进程运行（`data/debates/<id>.lock` 记录进程号），几个服务共用数据目录时不会重复续跑。

写到一半的发言会从头重写。演示模式的辩论只能在演示模式下续跑，真实辩论只能在真实模式下续跑。

## 博查搜索记录

每次调用博查都会被记录下来，包括时间、搜索词、返回条数、新增网页数、耗时和博查返回的 log_id，失败时还有原因：

- 实时写入页面的运行日志，同时在启动平台的终端里打印 `[博查] …` 行；
- 赛后在每位辩手的「检索记录」里可以看到完整列表，可用时间和 log_id 在博查控制台的账单明细中对照；
- 没有配置 `BOCHA_API_KEY` 时，辩手不检索，只能进行推理论证。

## 裁判组

| 裁判 | 侧重 |
|---|---|
| 逻辑裁判 | 推理链是否完整，只罗列引用的论点明显扣分 |
| 证据裁判 | 证据质量、引用诚信、质疑与核查结果 |
| 交锋裁判 | 攻防与回应、质询中谁拿到了让步 |
| 观众代表 | 说服力与表达 |
| 价值裁判 | 价值权衡与现实影响 |

每位裁判对双方的四个维度（论证质量、证据运用、交锋反驳、表达说服）各打 1-10 分，给八位辩手各打个人分（60-100），并投票给一方。可选 1、3、5 人，按表中顺序取前 N 位。胜负和最佳辩手完全由代码计算。

## 目录结构

```
src/
  server.ts               Express 服务：REST + SSE 实时推送
  config.ts               环境变量配置
  types.ts                领域模型（辩手、证据、发言、质疑、裁决）
  llm/models.ts           可选模型目录：DeepSeek / 智谱 / 千问，各家的思考强度档位与请求参数
  llm/client.ts           模型 API 封装（OpenAI 兼容格式）：JSON 结构化输出、函数调用循环、断线重试、错误翻译
  search/bocha.ts         博查 Web Search API 封装：请求排队限速、log_id
  search/page.ts          打开网页、提取正文、核对摘录
  agents/
    debater.ts            辩手 Agent：职责、可见范围、构思与撰写
    personas.ts           八位辩手的人设：论证习惯、语言风格、招牌打法、检索偏好
    researcher.ts         辩手的检索：搜索 → 打开网页核对 → 整理证据 → 逐字核对
    factcheck.ts          中立的证据核查员
    judge.ts              裁判人设、评分、主裁判综述
    schemas.ts            各 Agent 的结构化输出格式（zod）
    index.ts              Agent 工厂接口
  debate/
    orchestrator.ts       赛程编排：构思 → 撰写 → 校验与修改 → 公开 → 质疑核查
    validator.ts          发言、构思、质疑的校验
    citation.ts           引用写法、引用密度、数据点去重、发言时长
    scoring.ts            分数归一、计票与最佳辩手
    transcript.ts         按可见范围把辩论记录渲染为模型输入
    store.ts              内存 + JSON 落盘（data/debates/）
  mock/mockAgents.ts      演示模式的占位实现
  demo/placeholder.ts     动态演示：解析实录、评委点评和辩手资料文件夹
public/                   前端（原生 HTML/JS，无需构建）
  live.html / live.js     辩论直播页
  demo.html / demo.js     辩论动态演示页（占位内容）
```

## 配置项（.env）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `DEEPSEEK_API_KEY` | — | DeepSeek API 密钥 |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | DeepSeek API 地址 |
| `ZHIPU_API_KEY` | — | 智谱 API 密钥（bigmodel.cn），使用 GLM 模型时需要 |
| `ZHIPU_BASE_URL` | `https://open.bigmodel.cn/api/paas/v4` | 智谱 API 地址 |
| `DASHSCOPE_API_KEY` | — | 阿里云百炼 API 密钥，使用千问模型时需要 |
| `DASHSCOPE_BASE_URL` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 百炼 OpenAI 兼容地址（也可以换成业务空间专属域名） |
| `DEBATE_MODEL` | `deepseek-flash` | 表单里双方模型的默认选项（发起辩论时可按队伍更换） |
| `DEBATE_REASONING_EFFORT` | 模型默认档位 | 表单里思考强度的默认选项 |
| `JUDGE_MODEL` | `deepseek-flash` | 裁判组与证据核查员 |
| `JUDGE_REASONING_EFFORT` | 模型默认档位 | 裁判与核查的思考强度（该模型不支持时按低 / 中 / 高换算到最接近的档位） |
| `BOCHA_API_KEY` | — | 博查搜索 API 密钥；不填则辩手不检索 |
| `WEB_SEARCH_RESULTS_PER_QUERY` | `8` | 每次搜索返回的网页条数（1-50） |
| `SEARCHES_PER_DEBATER` | `3` | 每位辩手赛前检索次数（只有赛前准备可以检索） |
| `EVIDENCE_PER_SIDE` | `20` | 每方证据库最多收集几条（最多 30），按辩位平均分给四位辩手 |
| `MAX_EVIDENCE_USED_PER_SIDE` | `9` | 每方全场最多使用几条证据（首次在发言中引用算一条） |
| `PAGE_FETCH_TIMEOUT_MS` | `8000` | 打开网页核对原文的超时 |
| `BLOCKED_DOMAINS` | — | 额外屏蔽的站点（逗号分隔） |
| `CROSS_QUESTIONS_PER_TARGET` | `2` | 三辩向对方一辩、二辩各提几问 |
| `FREE_DEBATE_TURNS` | `8` | 自由辩论总发言次数 |
| `MAX_CHALLENGES_PER_SIDE` | `3` | 每方最多质疑对方证据的次数 |
| `MAX_EVIDENCE_PER_POINT` | `2` | 每个论点最多引用几条证据 |
| `MAX_CITATION_RATIO` | `0.45` | 一段发言中含引用的句子最多占比 |
| `SPEECH_CHARS_PER_MINUTE` | `240` | 正常语速（每分钟字数），用于估算发言时长 |
| `OPENING_MINUTES` | `8` | 立论目标时长（分钟） |
| `OPENING_MIN_MINUTES` | `6` | 立论最短可接受时长（分钟），更短则要求扩充 |
| `OPENING_MAX_MINUTES` | `9` | 立论最长可接受时长（分钟），更长则要求删减 |
| `PORT` | `3000` | 服务端口 |
| `DEBATE_MOCK` | `0` | 设为 `1` 进入演示模式 |

各家的 JSON 模式只保证输出是合法 JSON，不校验结构（千问在思考模式下连这一点也不保证），长篇中文发言偶尔还会在字符串里夹带英文双引号或真实换行：系统把各 Agent 的 JSON Schema 写进提示词，返回后先做保守修复（转义正文里的引号和换行），再用 zod 校验；仍不合格就把问题告诉模型重试，最多 3 次。解析失败的原始输出保存在 `data/debug/`，便于排查。

博查按次计费（Web Search API 0.036 元/次）。默认配置下一场辩论约 30 次搜索（8 位辩手各 3 次，以及每次质疑核查 1 次），约 1 元。免费档限 1 次/秒，系统会把所有搜索排队串行执行。
